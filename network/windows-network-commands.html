ping

상대가 응답하는지, 얼마나 빠른지 확인하고, 문제 구간을 단계별로 좁혀 봅니다.

ping은 상대에게 ICMP “에코 요청”을 보내고 “에코 응답”이 돌아오는 시간을 잽니다. 소리를 지르고 메아리가 돌아오는 시간을 재는 것과 같습니다.

ping google.com기본 4회 전송
ping -n 10 8.8.8.810회 전송
ping -t 8.8.8.8멈출 때까지 계속 (Ctrl+C로 종료)
ping -l 1000 8.8.8.8패킷 크기를 1000바이트로
ping -4 google.comIPv4로 강제
 출력 예시
Ping google.com [142.250.207.46] 32바이트 데이터 사용:
142.250.207.46의 응답: 바이트=32 시간=31ms TTL=116
142.250.207.46의 응답: 바이트=32 시간=32ms TTL=116
142.250.207.46의 응답: 바이트=32 시간=31ms TTL=116
142.250.207.46의 응답: 바이트=32 시간=33ms TTL=116

142.250.207.46에 대한 Ping 통계:
    패킷: 보냄 = 4, 받음 = 4, 손실 = 0 (0% 손실),
왕복 시간(밀리초):
    최소 = 31ms, 최대 = 33ms, 평균 = 32ms
이런 메시지가 나오면의미
요청 시간이 만료되었습니다.응답이 안 옴. 상대가 꺼졌거나, 경로 문제, 또는 방화벽이 ping을 막는 경우
대상 호스트에 연결할 수 없습니다.가는 길 자체를 못 찾음 (라우팅 문제, 게이트웨이 문제)
호스트 ○○을(를) 찾을 수 없습니다.이름을 IP로 못 바꿈. 대부분 DNS 문제

5단계 진단법 (가까운 곳부터 먼 곳으로)

  1. ping 127.0.0.1: 실패하면 내 PC의 네트워크 기능 자체 문제
  2. ping 내IP: 실패하면 랜카드나 드라이버 문제
  3. ping 게이트웨이: 실패하면 공유기까지의 연결(Wi-Fi, 케이블) 문제
  4. ping 8.8.8.8: 실패하면 공유기 밖, 인터넷 회선 문제
  5. ping google.com: 4번은 되는데 이것만 실패하면 DNS 문제

TTL은 패킷이 라우터를 지날 때마다 1씩 줄어드는 수명입니다. Windows는 보통 128, Linux는 64에서 시작하므로, 남은 값을 보면 상대 OS와 거쳐 온 라우터 수를 대충 짐작할 수 있습니다. 위 예시의 116은 128에서 12번 줄어든 값으로 볼 수 있습니다.

tracert, pathping

목적지까지 어떤 라우터를 거쳐 가는지, 어디서 느려지는지 확인합니다.

tracert는 TTL을 1, 2, 3… 으로 늘려 가며 패킷을 보냅니다. TTL이 0이 되는 라우터가 “시간 초과” 응답을 보내 주기 때문에, 그 응답을 모으면 경로 지도가 완성됩니다.

tracert google.com경로 추적 (최대 30홉)
tracert -d 8.8.8.8라우터 이름 조회 생략, 훨씬 빠름
tracert -h 10 google.com최대 10홉까지만
pathping -n google.com구간별 손실률 측정 (수 분 소요)
 출력 예시
최대 30홉 이상의
8.8.8.8(으)로 가는 경로 추적:

  1     2 ms     1 ms     1 ms  192.168.0.1      ← 우리 집 공유기
  2     5 ms     4 ms     5 ms  10.32.0.1        ← 통신사 내부망
  3     *        *        *     요청 시간이 만료되었습니다.
  4     8 ms     7 ms     8 ms  112.189.28.69
  ...
  9    32 ms    31 ms    32 ms  8.8.8.8

추적을 완료했습니다.

* * *는 그 라우터가 응답을 안 해 주는 것일 뿐, 다음 줄이 정상으로 이어지면 장애가 아닙니다. 어느 줄부터 시간이 확 뛰고 그 뒤로도 계속 높다면, 그 구간이 느린 곳입니다.

종합 실습: 장애 해결 시나리오

증상만 보고 어떤 명령을 어떤 순서로 쓸지 직접 정해 봅니다. 조별로 먼저 토론한 뒤 해설을 펼치세요.

시나리오 A. “인터넷이 아예 안 돼요.” ipconfig를 보니 IPv4가 169.254.37.12

원인: DHCP 서버(공유기)에서 IP를 못 받아 Windows가 임시 주소를 스스로 붙인 상태입니다.

순서: ipconfig /release → ipconfig /renew → 그래도 안 되면 케이블, Wi-Fi 연결, 공유기 재부팅 확인 → ping 게이트웨이로 확인.

시나리오 B. ping 8.8.8.8은 되는데 ping google.com은 “호스트를 찾을 수 없습니다”

원인: 인터넷 회선은 정상이고 이름 변환(DNS)만 실패한 상황입니다.

순서: nslookup google.com 실패 확인 → nslookup google.com 8.8.8.8은 성공하는지 확인 → 성공하면 DNS 서버 설정 문제 → ipconfig /flushdns 후 네트워크 설정에서 DNS를 8.8.8.8 등으로 변경.

시나리오 C. 해외 사이트 하나만 유독 느려요

순서: ping으로 평균 시간과 손실률 확인 → tracert -d 대상으로 시간이 급증하는 홉 찾기 → pathping으로 그 구간 손실률 확인.

해외로 나가는 구간에서 시간이 늘어나는 것은 물리적 거리 때문에 정상일 수 있습니다. 손실이 계속 생기는지가 핵심입니다.

시나리오 D. 아무것도 안 켰는데 네트워크 표시등이 계속 깜빡여요

순서: netstat -ano로 ESTABLISHED 연결 확인 → 외부 주소와 PID 기록 → tasklist /fi "PID eq 번호"로 프로그램 확인 → 모르는 프로그램이면 작업 관리자에서 파일 위치 확인.

대부분은 Windows 업데이트, 클라우드 동기화, 메신저 같은 정상 프로그램입니다.

마무리 퀴즈 (5문제)

Q1. 내 PC의 MAC 주소와 DNS 서버를 한 번에 보려면?

ipconfig /all

Q2. ping 결과의 TTL=55. 상대는 Windows일까 Linux일까?

Linux 계열일 가능성이 큽니다. 64에서 9번 줄었다고 보는 게 자연스럽습니다. (128에서 73번 줄었다고 보기엔 홉이 너무 많음)

Q3. 사이트 IP가 바뀌었는데 내 PC만 옛날 주소로 접속해요. 어떤 명령?

ipconfig /flushdns로 DNS 캐시를 비웁니다.

Q4. tracert 중간에 * * * 가 한 줄 있고, 그 뒤는 정상. 장애일까?

아닙니다. 그 라우터가 응답을 보내지 않도록 설정되어 있을 뿐, 패킷은 정상적으로 지나갔습니다.

Q5. 내 PC가 3389 포트를 열고 있는지 확인하는 명령은?

netstat -an | findstr :3389로 LISTENING 줄이 있는지 봅니다. 3389는 원격 데스크톱 포트입니다.
